# STHGroup — правила для нейросети, работающей с этим репозиторием

Сначала прочти **`ПОЛНОЕ ОПИСАНИЕ.md`** (там же история версий — последняя внизу раздела 8) — всё о программе: устройство, данные, решения автора, что не проверено.

## Как работать с автором (Глезерис Евгений Алексеевич)

- **Обновление правила 06.11.2026, последнее прямое указание автора:** «Сначала всё согласовываешь со мной визуально, потом вносишь правки». До любых изменений программы, в том числе мелких исправлений по скриншотам, сначала показать отдельный визуальный макет и дождаться явного согласования. Прежнее исключение «мелкие правки сразу» больше не действует. Молчание не считается согласованием. Подготовку макета не путать с изменением исходников или выпуском.

- Язык — русский. Автор не программист: отвечай коротко, итог первым, обычными словами, без внутренних названий инструментов.
- Перед работой — уточняющие вопросы, как можно больше, **только вариантами для выбора галочкой** (не просить расписывать ответы текстом).
- Любые изменения программы, включая мелкие исправления, сначала согласовать визуально. После явного одобрения показанного макета делать согласованные правки и выпуск без повторного запроса «поехали».
- **Всё по оформлению** (окна, PDF, значки, логотип, название, темы) — сначала варианты картинками, делать только после его выбора.
- Если автор сам точно сказал, что сделать (например, «кнопка напротив товара»), — не переспрашивать то же самое.
- Правки маленькие и по месту. Не переписывать то, о чём не просили.
- После каждой версии: честный список «не проверено» и **готовый текст для тестеров** (окно «что нового»): что изменилось и что проверить.
- Не просить в чат пароли, ключи, токены, адреса ящиков.
- Не говорить, что проверено на Windows или в настоящем БАЗИСе, если этого не было: проверки идут на Linux, в Node.js и Chromium.

## Общие правила

- Работают параллельно две нейросети: перед правкой `git pull`, после — `npm test`, коммит, `git push`. Конфликт — сначала слить (`git pull --rebase`), прогнать проверки.
- Перед выпуском: `git pull`, посмотреть `version` в `package.json` и последний выпуск на GitHub — новый номер должен быть больше последнего выпуска (две нейросети могут выпускать параллельно).
- Выпуск = поднять `version` в `package.json` и push в `main` (GitHub Actions соберёт и выпустит, программы обновятся сами). Не выпускать без зелёных проверок. Тег руками не отправлять.
- Окно `web/` — копия окна BazisReborn 2.2.1: правки в его файлах помечать комментарием `STHGroup`, держать минимальными; своё — в отдельных файлах (`ui/sth*.js`, `core/sth_order.js`, `core/linkparse.js`).
- Не переименовывать то, что нужно для совместимости с BazisReborn: формат `'benchmark-project'`, `.bmk`, `X-BM-Token`, объект `BM`, адреса `/api/*`.
- Скрипт выгрузки (`bazis/STHGroup_Export.js`) — исходник в UTF-8; в БАЗИС он уходит латиницей (`server.js → asciiScript`). После правки скрипта прогнать `node test/fixtures.js && node test/t_export.js`.
- Не класть в репозиторий пароли, ключи, личные данные автора, его базы (.FDB, .dbf, XML) и модели, скрипт «СМЕТА».
- Менять поведение — вместе с `README.md` / `ПОЛНОЕ ОПИСАНИЕ.md` и проверкой в `test/`.
